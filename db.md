# Plan: `ci db` — migration commands with ORM auto-detection

Goal: a `ci db <subcommand>` surface that works the same way regardless of
which ORM `ci init` set up in the target project (drizzle/typeorm/prisma),
by detecting the ORM and delegating to that ORM's own CLI underneath.

## Status

Shipped:

- `ci/config.json` — written by `ci init`, read by `ci db` for detection.
- TypeORM's `src/database/data-source.ts` (Gap 1) — `database.provider.ts`
  now imports it instead of building a second `DataSource`.
- `ci db init`, `ci db migrate` — real, for all three ORMs.
- `ci db migrate fresh` — real for Prisma (`migrate reset --force`) and
  TypeORM (`schema:drop` + `migration:run`); errors clearly for Drizzle
  (Gap 4, still open — no drop primitive).
- `ci db migrate refresh` — real for Prisma (identical to `fresh`); errors
  clearly for Drizzle (Gap 4) and TypeORM (revert-loop termination isn't
  implemented — see the mapping table).
- `ci db migrate rollback` — real for TypeORM (`migration:revert`, repeated
  `--step` times); errors clearly for Drizzle/Prisma (the underlying tools
  don't support it at all, not a gap in `ci`).
- `-y`/`--yes` and `-f`/`--force` on the destructive subcommands, gating on
  a confirmation prompt and `NODE_ENV=production`.

Not shipped: `ci db seed` (Gaps 2–3 — no seed script templates exist for
any ORM), TypeORM's `migrate refresh`.

---

## Command surface

```
ci db init                 # first-time setup: create + apply the initial migration
ci db migrate              # apply pending migrations
ci db seed                 # run the seed script
ci db migrate fresh        # drop everything, re-run all migrations from zero
ci db migrate refresh      # roll back all migrations, then re-apply them
ci db migrate rollback     # undo the last migration (or --step N)
```

**Naming decision:** the ask used Laravel's `migrate:fresh` colon style.
Recommending nested clap subcommands (`ci db migrate fresh`) instead of
literal colons — clap supports colon-named subcommands, but they're
awkward for shell completion and don't match this tool's existing
`ci db <verb>` shape. `fresh`/`refresh`/`rollback` become subcommands of
`migrate`, so `Commands::Db(db::Args)` → `db::Commands::Migrate(migrate::Args)`
→ `migrate::Action::{Run, Fresh, Refresh, Rollback}`.

`rollback` additionally takes `--step <N>` (default 1) where the underlying
tool supports it.

## Config file (`ci/config.json`)

Detect by **reading config `ci` writes itself**, rather than sniffing for
marker files. `ci init` gains one more output: a `ci/` folder at the
project root containing `config.json` — the CLI's own record of how the
project was scaffolded and what to run for it:

```json
{
  "ciVersion": "0.1.1",
  "orm": "drizzle",
  "driver": "pg",
  "packageManager": "npm"
}
```

`driver` is present only when `orm` is `"drizzle"` (mirrors `--driver`
being ignored for the other two ORMs today). This file is checked into
git — it's project config a teammate running `ci db migrate` needs too,
not a local/machine-specific file like `.env`.

`ci db` reads `ci/config.json` from the current working directory to get
`orm` (and `driver`, when relevant) directly — no filesystem sniffing, no
ambiguity. An explicit `--orm` flag on `ci db` overrides the file, for the
rare case someone wants to run a one-off command against a differently-
configured checkout.

**Fallback for pre-existing projects:** a project generated by a `ci`
version before this file existed won't have one. Fall back to the marker-
file scan below only in that case, and print a note suggesting the user
run a (future) `ci db init` or similar to write `ci/config.json` so
later runs don't need to re-detect:

| ORM | Marker |
|---|---|
| Drizzle | `drizzle.config.ts` at project root |
| Prisma | `prisma/schema.prisma` |
| TypeORM | `src/database/data-source.ts` (see Gap 1 below — doesn't exist yet) |

If neither the config file nor a unique marker is found, error out with a
message naming what was (or wasn't) found rather than guessing.

## Per-ORM command mapping

| `ci db` subcommand | Drizzle (`drizzle-kit`) | Prisma | TypeORM |
|---|---|---|---|
| `init` | `generate` then `migrate` | `migrate dev --name init` | `migration:run` (after first `migration:generate`) |
| `migrate` | `migrate` | `migrate deploy` | `migration:run` |
| `seed` | run `src/database/seed.ts` (tsx) | `db seed` | run `src/database/seed.ts` (tsx) |
| `migrate fresh` | ⚠️ no built-in drop — see Gap 2 | `migrate reset` (drops, re-applies, re-seeds — one command covers both fresh *and* refresh) | `schema:drop` then `migration:run` |
| `migrate refresh` | ⚠️ same as `fresh` — no down-migration story, see Gap 2 | `migrate reset` (identical to `fresh` for Prisma) | loop `migration:revert` to zero, then `migration:run` |
| `migrate rollback` | ⚠️ not supported — see Gap 2 | ⚠️ not supported — Prisma has no single-migration undo, only `reset` | `migration:revert` (repeat `--step` times) |

The ⚠️ rows aren't oversights — they reflect real gaps in the underlying
tools, not something `ci` can paper over. For those, `ci db <subcommand>`
should print a clear error naming the limitation instead of silently doing
something misleading (e.g. "drizzle-kit has no rollback command; hand-write
a down migration or restore from a backup").

## Gaps to fill before this works end-to-end

1. **TypeORM has no CLI entrypoint yet.** `database.provider.ts`'s
   `DataSource` is currently constructed inline inside a Nest factory —
   fine for the app, but the TypeORM CLI (`migration:run`, `schema:drop`,
   etc.) needs a *standalone* exported `DataSource` instance to point at
   (conventionally `src/database/data-source.ts`, loaded via
   `typeorm-ts-node-commonjs`). Needs its own template, and
   `database.provider.ts`'s typeorm branch should probably import that
   shared instance instead of constructing a second one.
2. **Neither Drizzle nor TypeORM has a seed command.** Need a
   `src/database/seed.ts` template (writes some rows via the ORM's own
   client) plus a way to run it — `tsx` as a new devDependency, a
   `db:seed` package.json script per ORM.
3. **Prisma's `db seed` requires config** — a `"prisma": { "seed": "tsx
   prisma/seed.ts" }` block in `package.json` and a `prisma/seed.ts`
   template (different path convention than the other two, since Prisma
   keeps everything under `prisma/`).
4. **`migrate fresh` for Drizzle** needs *something* to drop with — no
   `drizzle-kit drop-database` equivalent exists. Options: shell out to
   `psql "$DATABASE_URL" -c "DROP SCHEMA public CASCADE; CREATE SCHEMA
   public;"` (needs `psql` on PATH — an extra runtime dependency this tool
   doesn't currently require), or connect via the driver already in
   `package.json` (`pg`/`postgres`) from a small throwaway Node script.
   Leaning toward the driver-based script since it needs no extra binary,
   but it's the least settled piece of this plan.

## Safety

`migrate fresh` and `migrate rollback` are destructive (drop tables / undo
committed migrations). Mirror the confirmation pattern `ci update` already
has (`src/commands/update/args.rs`'s `-y`/`--yes`): prompt unless `--yes`
is passed, refuse to run against `NODE_ENV=production` without an explicit
`--force` on top of `--yes`.

## Rust implementation shape (as built)

```
src/db_orm.rs         # DbOrm + DrizzleDriver — moved out of commands::init::args
                       # since both init (writing ci/config.json) and db (reading
                       # it) need the same enums

src/fs.rs              # FileSystem gained try_read_to_string (Ok(None) if missing) —
                        # it previously only supported writes; db needs to read
                        # ci/config.json and probe marker files

src/commands/init/
  project_config.rs    # serde_json::to_string_pretty over a small struct — no
                        # Tera involved, unlike the rest of init's output

src/commands/db/
  mod.rs               # dispatch + the actual npx invocations per ORM,
                        # guard_destructive (yes/force/production check) and
                        # confirm (stdin prompt, bypassed by --yes so tests
                        # never hit it)
  args.rs               # Args/Command, MigrateArgs/MigrateAction, RunArgs,
                         # DestructiveArgs, RollbackArgs (-y/-f)
  detect.rs              # reads ci/config.json; falls back to marker-file scan
```

Execution reuses `ctx.commands` (the existing `CommandRunner` trait) —
`ci db migrate` becomes `ctx.commands.run("npx", &["drizzle-kit",
"migrate"], &root)`. Chose direct `npx` invocation over the project's own
`npm run db:*` scripts (even though `init` writes some) — one dispatch
path for all three ORMs instead of depending on script names staying in
sync with what `ci db` expects.

`guard_destructive` takes `is_production: bool` as a plain parameter
rather than reading `std::env::var("NODE_ENV")` itself — mutating a
process-global env var from parallel tests would be flaky, so `run()`
reads it once and passes it down, keeping the guard's logic pure and
directly testable.

1. ~~**`ci/config.json`**~~ — done. `DbOrm`/`DrizzleDriver` moved to
   `src/db_orm.rs`, `src/commands/init/project_config.rs` renders it,
   wired into `init::run`.

   `database.provider.ts`'s typeorm branch now imports the shared instance.
3. Gaps 2–3 (seed scripts, Prisma seed config) — still open, blocks
   `ci db seed`.
4. ~~`detect.rs`~~ — done. Reads `ci/config.json`, falls back to the
   marker-file scan. `FileSystem` gained `try_read_to_string` to support
   this (it previously only supported writes).
5. ~~`ci db init` / `ci db migrate`~~ — done, all three ORMs, via direct
   `npx <tool> ...` invocation (not the `package.json` scripts — simpler,
   doesn't depend on script definitions staying in sync).
6. `ci db seed` — still open, needs step 3 first.
7. ~~`ci db migrate fresh` / `refresh` / `rollback`~~ — done where safely
   resolvable (see Status above); the remaining gaps are honest `bail!`s,
   not silent wrong behavior.
8. ~~Tests~~ — `commands/db/tests.rs` (dispatch, one fixture per ORM via
   `NoopCommandRunner`) and `commands/db/detect/tests.rs` (config-file +
   marker-scan detection via `InMemoryFileSystem`).
